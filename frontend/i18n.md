# 다국어(한국어·영어)

> 갱신일: 2026-10-07
> 브랜치: `loresentry-frontend` `feat/i18n` · `loresentry-authentication`·`loresentry-content`·`loresentry-gateway` `feat/i18n`

한국에서 접속하면 한국어, 그 밖에서는 영어로 보인다. 사용자가 언어를 고르면(화면의 언어 단추, 계정
설정) 그 선택이 위치보다 앞선다. 로그인한 사용자는 계정에 적힌 언어를 따른다.

## 1. 정한 것과 이유

| 항목 | 정한 것 | 이유 |
| --- | --- | --- |
| 언어를 정하는 곳 | CDN(CloudFront Function)이 요청마다 고른다 | 정적 export 라 Next 서버가 없다. 나라 정보(`CloudFront-Viewer-Country`)는 CDN 에만 있다 |
| 빌드 | 한국어판·영어판을 따로 export 해 버킷 `/ko/`, `/en/` 에 둔다 | 문구가 빌드 때 굳어 첫 화면부터 그 언어다. 깜빡임·하이드레이션 불일치가 없다 |
| 주소 | 언어 없는 주소가 기본. `/ko/...`, `/en/...` 도 열린다 | 작업공간 링크·로그인 복귀 주소가 언어와 무관하게 같다. 언어별 주소는 검색엔진(hreflang)용 |
| 문구 사전 | 열쇠 = 한국어 원문, 영어만 사전에 둔다 | 코드에 한국어가 그대로 남아 읽기 쉽고, 한국어판 출력이 바뀌지 않는다 |
| 계정 언어 | `users.locale` (`ko`/`en`/`NULL`) | 어느 기기에서 들어와도 같은 언어. 처음 로그인할 때 그때 보던 언어를 적는다 |
| 서버가 만드는 데이터 | 약관 번역 테이블, 영어 예시 프로젝트 | 약관 동의와 예시 프로젝트는 서버 데이터라 화면 번역으로는 영어가 되지 않는다 |
| 분류 폴더 이름 | 화면이 폴더 코드로 이름을 붙인다 | `base_folders.name` 은 한국어지만 화면은 이미 코드(`CHARACTER` 등)로 이름을 정한다. DB 변경 불필요 |

## 2. 언어를 고르는 순서 (CloudFront Function)

`loresentry-frontend/docs/deploy/cloudfront-rewrite.js`

1. `ls_locale` 쿠키 — 사용자가 고른 언어, 로그인한 계정의 언어
2. `CloudFront-Viewer-Country` — `KR` 이면 `ko`, 그 밖은 `en`
3. `Accept-Language` — 나라를 모를 때만. 첫 언어가 `ko` 면 `ko`
4. `en`

언어 없는 경로는 `/<언어>` 를 앞에 붙여 그 판의 파일을 준다. `/ko/...`, `/en/...` 은 그대로 준다. 이렇게 들어온
탭은 세션 쿠키 `ls_locale` 이 그 언어로 잡혀, 앱 안에서 이동해도 같은 언어를 유지한다(남이 보낸 링크
하나로 언어가 영구히 바뀌지 않게 세션 쿠키다).

## 3. 계정 언어

| 시점 | 동작 |
| --- | --- |
| 로그인 직후(`SessionGate`) | 계정 언어가 `NULL` 이면 지금 보는 언어를 `PUT /auth/users/me/locale` 로 적는다 |
| 계정 언어 ≠ 지금 언어 | `ls_locale` 쿠키를 계정 언어로 바꾸고 다시 연다. 탭마다 한 번만(무한 새로고침 방지) |
| 언어 단추·계정 설정 | 계정에 적고(로그인 시), 쿠키를 바꾸고 다시 연다 |

## 4. 서버 계약

| 서비스 | 바뀐 것 |
| --- | --- |
| authentication | `V6` `users.locale` 컬럼, `V7` `terms_version_translations` 테이블, `V8` 영어 약관 v0. 프로필 응답 `locale`, `PUT /auth/users/me/locale`, `GET /auth/terms?locale=en` → 번역본과 `locale` 필드. Google 이름이 비면 표시 이름을 이메일 앞부분으로(예전에는 "사용자") |
| content | `POST /projects/sample?locale=en` → 영어 예시 프로젝트(`sample/glass-garden.en.json`) |
| gateway | 위 필드·경로를 브라우저에 그대로 연다. `locale` 은 `ko`/`en` 만 위로 넘긴다 |

모두 하위 호환이다. `locale` 을 보내지 않는 예전 프론트는 지금과 같은 한국어 동작을 받는다.

배포 순서: authentication·content → gateway → frontend. 예전 인증 서버는 `PUT /auth/users/me/locale` 에 500 을
돌려준다(프론트는 이 실패를 무시하고 화면을 그대로 쓴다).

## 5. 프론트 구조

```text
src/i18n/
  locale.ts        LOCALE (빌드 상수), Locale, 언어 이름
  t.ts             t("한국어", { 값 }) — 한국어판은 열쇠, 영어판은 사전
  rich.tsx         tRich — 문장 안의 강조·링크
  en/*.ts          영어 사전. 영역마다 파일 하나(common, landing, onboarding, shell, workspace, editor, help, mock)
  preference.ts    ls_locale 쿠키, 언어 바꾸기, 계정 언어 따르기, <head> 세션 쿠키 스크립트
  coverage.test.ts 사전을 거치지 않은 한국어 문자열을 막는다
src/features/locale/  언어 단추(LanguageSwitch), useLocaleSwitch
src/shared/format.ts  날짜·숫자 표기(언어별)
public-en/            영어판에만 덮어쓰는 정적 파일(약관·개인정보처리방침)
```

새 문구를 더할 때는 한국어를 `t("…")` 로 감싸고 그 영역의 `en/*.ts` 에 영어를 적는다. 영어가 빠지면
타입 검사가 실패하고, 감싸지 않으면 `coverage.test.ts` 가 실패한다.

## 6. 빌드·확인·배포

```bash
pnpm dev                                  # 한국어
NEXT_PUBLIC_LOCALE=en pnpm dev            # 영어
pnpm build:locales                        # dist/ko, dist/en
COUNTRY=US pnpm serve:locales             # CloudFront 함수를 거친 결과를 로컬에서 (http://localhost:4000)
pnpm check:cdn                            # CI 와 같은 검사(두 판 모두 빌드·검증)
```

테스트는 vitest 프로젝트 두 개로 돈다. 대부분은 한국어판(`ko`)에서, `*.en.test.*` 는 영어판(`en`)에서.

배포는 CI 가 두 판을 `/ko/`, `/en/` 에 올리고 버킷 맨 위에 한국어판을 남긴다. **콘솔 작업 두 가지**가 한 번
필요하다(`loresentry-frontend/docs/deploy/README.md`).

1. origin request policy 에 `CloudFront-Viewer-Country` 를 넣어 기본 동작에 연결한다.
2. 두 판이 올라간 뒤 CloudFront Function 코드를 바꾸고 publish 한다.

순서를 지키면 중단이 없다. 함수를 바꾸기 전까지는 지금처럼 맨 위의 한국어판이 서빙된다.

## 7. 남은 일

- 영어 약관·개인정보처리방침은 번역본이다. 공개 전에 법적 검토가 필요하다.
- AI 기능(그래프 최신화, AI 챗)은 아직 서버가 없다. 붙일 때 출력 언어를 원고 언어에 맞춰야 한다.
